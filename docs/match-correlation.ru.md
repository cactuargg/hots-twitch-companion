# Match Correlation — PR #19

## Исследование и выбранный способ

Исходная логика принимала первый свежий реплей с выбранным игроком. Имя или
ToonHandle идентифицируют игрока, но не матч. Совпадение состава тоже не отличает
повторную игру тех же участников; random seed не имеет гарантии уникальности.

В [реальных данных Heroes.StormReplayParser](../testdata/battlelobby/README.md)
найдена проверяемая пара: отдельный `StormLeague1_89566.battlelobby` и
`HanamuraSL1_89566.StormR`. MPQ-элемент `replay.server.battlelobby` второго файла
побайтно совпадает с первым. Все десять ToonHandle совпадают с `replay.details`;
исход первого участника — loss. `m_timeUTC` в details — FILETIME
`133186776809519636` (Unix milliseconds `1674204080951`).

Сравниваем SHA-256 **содержимого BattleLobby**, полученного из этих двух мест.
Это доказательство равенства содержимого, а не новый общий Match ID. Для иной
версии/режима сервер может сохранить отличающиеся байты; тогда автоматического
расчёта не будет. Запасного сопоставления по seed, составу, имени или mtime нет.
Проверка не защищает от намеренной подделки локальных файлов.

## Привязка Prediction

При создании Prediction копируются последний снимок лобби, его ключ наблюдения
и выбранный ToonHandle в `active.match` (version 1). Копия состава не разделяет
изменяемый массив с `lastLobby`. Настройки игрока и новое лобби не меняют привязку.
Она сохраняется вместе с существующим ID/StartedAt Prediction в `state.json`.

Старый активный Prediction без `match` читается, но автоматически не привязывается
к текущему лобби. Пользователь решает его вручную или сверяет статус с Twitch.
Непрочитанное/неподдерживаемое лобби и выбор только по имени тоже оставляют ручной
расчёт доступным. Приложение не приписывает ToonHandle по совпадению ника.

## Условия автоматического Win/Loss

1. Поддержанная привязка с успешно разобранным лобби. Время изменения лобби —
   не более чем за 120 секунд до создания Prediction и не позднее него более
   чем на 2 секунды. Это ограничение наблюдения, не самостоятельное доказательство.
2. Режим Quick Match (50001), Unranked Draft (50051), Storm League (50091) или
   ARAM (50101), размер `5v5`, десять уникальных human/Part ToonHandle —
   либо кастомное лобби `5v5`, где каждый human/Part слот проверен по
   уникальному ToonHandle, а AI-слоты (Comp) не имеют ToonHandle.
   Наблюдатели исключаются по явной роли Watc. Неполные составы и кастомные
   лобби без людей требуют ручного решения. Поддержанные build перечислены в
   `testdata/battlelobby/README.md`.
3. Полный обход настроенных папок реплеев: до 20 000 элементов и 128 файлов с
   mtime не раньше наблюдаемого лобби минус 2 секунды. Превышение лимита или ошибка
   обхода блокирует расчёт вместо молчаливого усечения списка до последних 12.
   Отсутствующий стандартный OneDrive/Documents путь допустим; отсутствующий
   явно заданный путь — ошибка.
4. Файлы ждут 8 секунд после mtime. Проверяются метаданные между обходом и чтением,
   до и после ограниченного чтения (64 MiB), а также подмена файла. Все MPQ-элементы
   извлекаются из одного массива байтов. Проверки метаданных не гарантируют
   обнаружение записи того же размера с восстановлением timestamp.
5. SHA-256 встроенного BattleLobby равен закреплённому. Повторный разбор его
   состава совпадает с сохранёнными данными. Иное содержимое исключается.
6. Игровой `m_timeUTC` не раньше времени наблюдения минус 2 минуты и не позже
   текущего времени плюс 2 минуты. Старый реплей не становится свежим от изменения
   файлового mtime. Отсутствующий/неправильный clock либо сильное расхождение часов
   блокируют расчёт. Не предполагается, что это точное время экрана загрузки.
7. Все участники details сверяются с ростером: каждый human ToonHandle из
   лобби присутствует без дубликатов. Для матчмейкинга — десять человек,
   две команды по пять. Для кастомных лобби AI-записи имеют синтетический
   ToonHandle без `-Hero-` и проверяются только по команде и исходу;
   дополнительный Hero-handle вне ростера блокирует расчёт. Внутри каждой
   команды исход согласован, у команд — противоположный. Игрок из привязки
   обязательно участник.
8. Подходит ровно один вариант полного реплея. Побайтно одинаковые копии файла
   считаются одной записью; два разных файла с подходящими данными — неоднозначность,
   даже если объявленный исход одинаков. Нечитаемый/пишущийся свежий файл не даёт
   проигнорировать возможного второго кандидата.

Когда подходящих файлов несколько, неоднозначность сохраняется в привязке.
Удаление одного файла или перезапуск не разрешает выплату. Повторное наблюдение
одинакового содержимого лобби с новым ключом тоже фиксирует неоднозначность:
надёжно отличить повторный матч от переписывания файла мы не можем. Наблюдение
другого лобби не меняет старую привязку; старый матч всё ещё можно подтвердить
его собственным реплеем.

## Интерфейс и границы

Используется существующая строка диагностики, новых панелей нет. Причины:
`correlation_unavailable`, `correlation_mismatch`, `correlation_incomplete`,
`correlation_ambiguous`. Они видны и после ручной перепроверки при остановленном
мониторинге. Ручные Win/Loss/Cancel остаются доступны с прежними подтверждениями.
Перепроверка использует ровно тот же gate и проверяет прежние ID/StartedAt.
Существующая отмена по 100-минутному тайм-ауту сохранена.

Матрица тестов: реальная пара, неправильный состав/clock, изменённый mtime,
совпадающий seed без совпадения байтов, дубликаты/два результата, запись/повреждение
файлов, лимиты обхода, короткий матч, совпадение за пределами первых 12 файлов,
фиксация привязки при создании, смена настроек, перезапуск, устаревший recheck,
нулевые Twitch-запросы при неоднозначности и ровно один mock PATCH правильному
Prediction при подтверждённом результате. Реальные баллы в тестах не используются.

PR #20 (полный жизненный цикл и v0.8.0) и desktop/UI-миграция сюда не входят.
