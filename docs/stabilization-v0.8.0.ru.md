# Stabilization — подготовка v0.8.0

## Исследование

После PR #19 проверка матча стала строгой, но вокруг неё оставались проблемы:
cooldown пропускал следующий быстрый матч; наблюдение нового лобби при активном
Prediction не сохранялось для последующего создания; HTTP 200 от PATCH считался
достаточным подтверждением; память обновлялась раньше успешной записи на диск.
Потерянный ответ оставлял возможность выбрать противоположный исход.

В [Twitch API](https://dev.twitch.tv/docs/api/reference/#end-prediction) разрешены
ACTIVE → LOCKED/RESOLVED/CANCELED и LOCKED → RESOLVED/CANCELED. Поэтому короткий
матч может завершаться без ожидания всего окна ставок. Отдельный принудительный
LOCKED не нужен; время окна по-прежнему оценивается локально, а не выдаётся за
подтверждённый серверный статус.

## Реализация

- `active.settlement` хранит исход и источник решения до сетевого эффекта.
  JSON записывается во временный файл с `Sync`, затем заменяет основной.
  `updateAndSave` обновляет память после успешной записи.
- Перед первым и повторным PATCH выполняется GET точного ID. ACTIVE/LOCKED
  разрешают выбранный переход. Подтверждённый такой же результат не PATCH-ится
  повторно. Другой завершённый результат записывается как фактический исход Twitch.
- PATCH требует точного ID/финального статуса/победителя в ответе. Ошибка сети,
  пустой/неправильный HTTP 200 вызывают проверочный GET. Противоречивый PATCH без
  подтверждения GET не очищает активное состояние.
- Неизвестный результат сохраняет намерение. Противоположный Win/Loss/Cancel
  блокируется; Sync доступен. При мониторинге попытка возобновляется после
  перезапуска с тем же исходом, даже без нового реплея. Повтор идёт через 10–60
  секунд; заголовки 429 Retry-After/Ratelimit-Reset могут увеличить задержку.
  Тайм-аут матча не превращает ожидающий Win в Cancel.
- При ошибке окончательного сохранения остаётся активный ID и намерение.
  Следующий запуск сверяет уже завершённый Prediction и повторяет локальную запись.
  При сбое записи ID после создания он остаётся в памяти текущего процесса;
  после перезапуска неизвестный прогноз нужно проверить на Twitch.
- `pendingLobby` сохраняет последнее свежее наблюдение следующего матча, пока
  предыдущий завершается. Очередь переживает перезапуск; старше 120 секунд она
  отбрасывается. Новый снимок вытесняет старое ожидание. Создание не использует
  прежнюю привязку активного Prediction и не ждёт двухминутного cooldown.
- Ключ наблюдения и `lastCreatedLobbySHA` сохраняются до создания. Потерянный POST
  не повторяется на следующем tick/после перезапуска. Прогноз по заголовку не
  присваивается приложению. Для нового матча сначала проверяется, нет ли на канале
  ACTIVE/LOCKED прогноза. Если создание неизвестно, проверь Twitch; для того же
  лобби автоматического повтора не будет.
- Последние 64 обработанных SHA лобби сохраняются, чтобы повтор предыдущего
  лобби после следующего матча тоже не создавал новый прогноз. В симуляции StartedAt нового
  Prediction позже предыдущего завершения, чтобы старые кнопки не совпали по ID/времени.
- В существующих строках показаны ожидающий исход и ошибки даже при остановленном
  мониторинге. Противоположное ручное действие не отправляется из UI; сервер
  независимо проверяет запрет. Новых панелей/кнопок нет.

## Матрица автоматических проверок

| Сценарий | Ожидаемое поведение |
| --- | --- |
| ACTIVE/LOCKED → Win/Loss/Cancel | GET, сохранённое намерение, один PATCH, проверенный ответ |
| Уже завершён на Twitch | Фактический результат без PATCH |
| Потерянный ответ после успешного PATCH | GET подтверждает успех, второго PATCH нет |
| Сеть недоступна, затем перезапуск | Намерение остаётся; GET восстанавливает исход |
| HTTP 200 с пустым/чужим/противоречивым ответом | Без подтверждения не очищать Prediction |
| HTTP 401/429/503 | Нет ложного успеха; намерение сохранено, 429 задерживает повтор |
| Не удаётся сохранить намерение | Ни одного Twitch-запроса |
| Не удаётся сохранить окончание | Восстановление по ID без повторной мутации |
| Противоположный исход при неизвестном результате | Блокировка на сервере и в UI |
| Отменённый контекст | Нет эффекта до начала операции |
| Короткий и следующий матч, очередь + перезапуск | Оба результата свои, cooldown не пропускает матч |
| Повтор лобби, неизвестный POST | Нет повторного создания |
| Следующее лобби устарело, старый Win ожидает | Очередь отбрасывается, Win не меняется на Cancel |
| Локальный сервер на Windows | Встроенная HTML, CSP, версия API, защищённый Quit |

Сохраняется матрица парсера/корреляции PR #18–19. Вариант лобби с изменённым
косметическим хвостом и MPQ-контейнеры сценариев синтетические и явно отмечены;
они не выдаются за независимые реальные матчи.

## Выпуск и ограничения

Версия API статуса/README — 0.8.0. `build.ps1` и Actions запускают Go/JS проверки
и Go vet. ZIP содержит EXE, READMEs, LICENSE, RELEASE_NOTES и SHA256SUMS. Public
Client ID из Variables встраивается без Client Secret/токенов. Ветка/PR не создают
тег и не публикуют Release.

Поддержка BattleLobby ограничена четырьмя build и десятью людьми 5v5.
Правила [PR #19](match-correlation.ru.md) сохранены. Sync файла не обещает защиту
от любого сбоя питания файловой системы. Если запись не состоялась, новые эффекты
блокируются; потерянные до диска сведения нельзя гарантированно восстановить.
Неизвестный POST требует проверки на Twitch.

Проверка HTTP-сервера не равнозначна ручной проверке видимого Edge-окна или реальных
выплат. Эти проверки остаются перед выпуском для живого канала. Desktop shell,
трей и редизайн сюда не входят (PR #21–22).
